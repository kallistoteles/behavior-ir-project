## What prior experiments answered

The Core031 `specs/031-scalable-execution-evidence/profiling/single-create-20261028/report.md` and its `baseline.json`, `instrumented.json`, `profile-summary.json`, `instrumentation.patch` already establish a large repeated full record: at N8192, 4,085,191 canonical bytes, roughly 79% trace. The separate uninstrumented median is about 277 ms evaluate / 1,658 ms commit; serializing the ready decision alone is about 39 ms. A representative instrumented commit attributes about 99 ms to two strict parses and 335 ms exclusive to record validators. Those timings belong to their frozen older source/instrumentation, not automatically to this restored revision.

That profile's rule-removal variants changed the module and output; they diagnose which rules cause bytes but are not exact-semantics optimizations. Its serializer-only control excludes construction, validation and hashing. Thus it answers whether repetition exists, not how much an exact-output implementation can remove.

Core032's `specs/032-transition-verification-study/investigation.md` and `evidence/source-costs.md` explicitly preserve these confounders. Campaign002 corrected B's repeated independent prefix reconstruction, but retained full snapshots, lifetime scans and full output. DAG transport traverses and expands complete observations; its lower raw bytes and larger gzip packet do not measure an incremental evidence engine. A's maintained-view results remain conservative co-checking results. None of these comparisons implements the two changes recommended here.

The three 20261028 architecture note groups recommend typed representations and justified reuse; they are architectural investigations, not evidence that a byte-preserving optimization already passed. Core032 already completed much of their proposed minimal-transition study. Repeating that broad study or adding another proof backend would not isolate the remaining processing cost.

## Concrete discriminating experiment

Use one fixed module/request/time/context and the existing output profile. Compare a 2×2 matrix, with the normal Core029 incremental route identical in all cells:

1. **Baseline:** unchanged capture and record reproduction.
2. **Capture only:** avoid discarded prefix observations; share one authenticated prestate within an operation; retain the prior exact after-state and initialized lifetime inventory for the next ordinary step. Update used IDs only from accepted authoritative event `created` inventories. Compare claims fieldwise without cloning. This is initially a single-owner InMemory harness experiment; it does not change Core's production export behavior.
3. **Decode only:** keep the initial strict decode and the existing profile/version checks and validators, but validate that same parsed JSON in `replay_profile` instead of calling stringify → `DecisionRecord::from_json` → strict decode. Do not bypass `validate_record08`, semantic reproduction, fact comparison, canonical hashing, backend event checking or authorization.
4. **Both:** establish interaction rather than adding separate speedups or phase medians.

Keep N and H independent: a small N sweep (128, 512, 2048, optionally 8192 after the small cases pass), plus fixed N with increasing command-only prefix history. Command-only prefixes grow history without growing live state or requiring creation-ID retention; add create/remove prefixes separately to exercise lifetime growth. Record actual output byte counts and exact record/event/command identities for every completed attempt. Use identical prepared/cold conditions across cells and retain initialization, prefix, evaluate, commit, snapshot/lifetime capture, export and contiguous whole-case time separately.

Count strict decode calls/bytes, snapshot exports, backend record reads and explicit materialization bytes. Use diagnostic builds only to explain work, and uninstrumented builds for timing. Existing `validation-work` byte counters must be disabled consistently or their additional serialization reported separately. Ready-record serialization is an output control, not a measured total lower bound. Identical bytes with fewer calls/bytes and lower contiguous time establish avoidable work; an unchanged residual slope does not prove that all residual work is necessary.

Require exact before/after operational state, error code/message/stage, complete record, ordering and duplicate command occurrences; `SemanticOutcome` alone is too coarse. Run replay and existing archived-profile/error/authorization gates. Include count 1000/1001, malformed/duplicate-key/noncanonical input at raw ingress, wrong/null/unknown fields, profile mismatch, lazy/overflow/first-error cases, reused IDs after deletion, reference removal, stale exact history, cold reopen and lost-ack original-event retry. Authorization controls must include required independent context and differing archived/current context; the ordinary study fixture uses policy `require:none` and cannot establish governance equivalence alone.

## Premises that must remain explicit

`Backend` promises consistent as-of reads and atomic CAS (`crates/behavior-store/src/lib.rs`: 47), but offers no general authenticated revision token proving that already observed content cannot be corrupted while the same head remains visible. A same-head wrapper cache must therefore stay scoped to exclusive, conforming InMemory ownership, or gain explicit invalidation/stability evidence. A cache keyed only by StateId/position is insufficient: lineage, exact record, module/schema/profile and lifetime inventory matter. It must not silently hide corruption/missing-history errors previously found by an export/scan. Recovery must rebuild and compare the complete inventory before reuse; failed/conflicting/unknown-ack publication must not advance it speculatively.

The decode-only arm has the narrower premise: the parsed JSON remains immutable within one call after strict ingress validation. It introduces no cross-operation authority or snapshot claim. This makes it the preferred first implementation if only one bounded change is practical. Full typed-validator or canonical-streaming redesign can follow once its distinct saving is measured. No production adoption follows from this audit.
